# Going nationwide

The plan for taking Hopline from the Northeast to every transit agency in the United States, and why the order matters. The
two decisions behind it (made with the owner): **generated schedule data lives on GitHub Pages, not in git**, and **agencies
are added automatically from the Mobility Database**, with hand-written config only for special cases.

## Why the current design cannot just be repeated

Today each agency is a folder of JSON committed to git, a provider file with its own literal `import()`, and a line in the
registry (about 25 MB for 60 agencies). Repeated for roughly 1,500 US agencies that is gigabytes in git, a registry of
thousands of lines, a build that bundles it all, and a home page that serializes every board's link into the HTML. Each
piece has a scalable replacement:

| Today | At national scale |
| --- | --- |
| Agency data committed to git | Generated by a job, published to GitHub Pages one file per agency, fetched on first use, least recently used evicted |
| One provider file per agency | One generic provider built at runtime from a catalog entry (`catalog/agencies.json`) |
| Hand-picked regions | Regions derived from agencies' service areas (metro clusters), by script |
| Every board link sent to the browser | The browser asks for the boards in view (`/api/boards?bbox=`) |
| Every agency tried by hand | A validator downloads, parses, builds and checks each candidate feed; bad ones are skipped and reported |
| Station search over every board | A server-side place index per region, queried with a prefix |

## Order of work

1. **Performance foundations** (this stage; each its own PR):
   1. *Data off git (done):* `npm run data:publish` packs each agency into `dist-data/<id>.json`; `publish-data.yml` puts them
      on Pages; with `HOPLINE_DATA_URL` set the server fetches an agency on first use and falls back to the bundled copy; at
      most `HOPLINE_MAX_RESIDENT` agencies stay in memory (least recently used dropped).
   2. *Lean polling (done, #60)* and the *positions-only feed* (next stage of the scaling review).
   3. *Boards by viewport (done):* `/api/boards?bbox=` and a page that carries only the boards where the map opens, so the HTML
      does not grow with coverage. (Station search still walks every board: it needs the server-side place index below.)
   4. *Load test (done):* `npm run loadtest` drives the API with simulated viewers and reports latency, errors and memory;
      its first run found, and this stage fixed, flights timing out under load. Run it before switching on a batch of agencies.
2. **Catalog (done) and generic providers:** `scripts/build-catalog.ts` reads the Mobility Database catalog, keeps agencies with a
   keyless static feed (live where a keyless real-time feed exists and answers, timetable-only otherwise), clusters them into
   regions, and writes `catalog/agencies.json`. A generic provider is created per entry at startup from the shared factories
   (`createLiveProvider`, `createTimetableProvider`) with the data host as its loader. The existing hand-tuned providers stay
   and win over a generated one for the same service.
3. **Ingestion at scale:** the weekly job processes agencies in batches (matrix jobs, each within its time limit), validates
   each (parses, has stops and trips in its horizon, live feed returns vehicles whose routes match the schedule), and
   publishes only what passes, with a report of what failed and why.
4. **Switch on regions in waves** (largest metros first), watching the load test and the status page after each.

## The catalog

`npm run catalog` (`scripts/build-catalog.ts`, logic in `scripts/lib/catalog.ts`) reads the Mobility Database's public CSV and
writes `catalog/agencies.json`: every US agency with a **keyless schedule feed** and a plausible service area, each with its
keyless real-time feeds where the catalog lists them, minus the agencies Hopline already serves by hand (matched by schedule
URL). First run (3 November 2026): **807 candidate agencies in 51 states, 139 with a keyless live vehicle feed**; most are in
California (125), New York (78), Washington (58), Oregon (55) and Colorado (49). Agencies behind a key (9 schedule feeds, about
170 live feeds) are left out until a key is provided. The catalog says what exists; the ingestion job (next stage) downloads
and validates each candidate before anything is served, because a listed feed can be stale, empty or mismatched to its live
feed (as PVTA's and Middletown's were).

## What stays hand-written

Special cases the catalog cannot derive: operators whose live feed names no trip or route (joins needed), merged station
names across operators (Penn Station), colors and badges, rail track from other feeds (Amtrak), schedule data that must be
downloaded by hand, and feeds behind a key (listed in the report, added when a key is provided).
